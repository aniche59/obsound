QUESTION 1: "WHAT REST API METHODS DO YOU USE AND HOW DO YOU TEST THEM IN POSTMAN?"
--------------------------------------------------------------------------------
ANSWER:
"Sir, we implemented a full RESTful CRUD API on /api/v1/tracks (Practical 6), 
which we tested and verified using Postman:

1. GET /api/v1/tracks
   - Purpose: Fetches the entire collection of sound nodes.
   - Idempotent: YES (Calling it 1 time or 100 times returns the exact same data without modifying the server).
   - Status Code: 200 OK.

2. GET /api/v1/tracks/:id
   - Purpose: Fetches a single sound node by its unique ID.
   - Idempotent: YES.
   - Status Code: 200 OK (or 404 Not Found if missing).

3. POST /api/v1/tracks
   - Purpose: Creates a brand new sound node from client JSON payload.
   - Idempotent: NO (Every repeated POST request creates a new record with a new ID).
   - Status Code: 201 Created.

4. PUT /api/v1/tracks/:id
   - Purpose: Full replacement/update of an existing sound node. The payload contains 
     the complete new state of the entity.
   - Idempotent: YES (Repeating the same PUT with the same payload results in the identical final state).
   - Status Code: 200 OK.

5. PATCH /api/v1/tracks/:id
   - Purpose: Partial update. For example, updating only the 'bpm' or adding a tag, 
     without resending the entire track record.
   - Idempotent: YES in our implementation (setting a specific property value).
   - Status Code: 200 OK.

6. DELETE /api/v1/tracks/:id
   - Purpose: Deletes a sound node from the database.
   - Idempotent: YES (Deleting the node once removes it; repeating the request still leaves it deleted).
   - Status Code: 200 OK or 204 No Content.

In Postman, we have an automated test collection (ObSound_REST_API.postman_collection.json) 
with pm.test() assertions verifying status codes, response times under 200ms, 
and schema validations."

QUESTION 3: "WHY USE MONGODB (NOSQL) INSTEAD OF RELATIONAL SQL (MYSQL / POSTGRES)?"
--------------------------------------------------------------------------------
ANSWER:
"Sir, there are three key architectural reasons why MongoDB is superior for ObSound:

1. Hierarchical Acoustic Vectors:
   Each sound node stores nested acoustic properties:
   {
     harmonicKey: 'D Minor',
     resonanceFrequency: 528,
     bpm: 140,
     acousticVectors: { danceability: 0.82, energy: 0.91 }
   }
   In relational SQL, storing this requires multiple normalized tables, foreign keys, 
   and expensive JOIN operations on every graph render. In MongoDB, it is stored 
   as a single native BSON document.

2. Dynamic Sonic Tag Arrays:
   Underground tracks have variable, user-generated tag arrays:
   ['dungeon-synth', 'dark-ambient', 'tape-decay', 'lo-fi']
   MongoDB natively indexes arrays. In SQL, querying arbitrary tags requires a 
   Tracks table, a Tags table, and a many-to-many junction table with multi-table JOINs.

3. Schema Flexibility for Underground Metadata:
   Different niche genres require arbitrary custom fields (e.g. Bandcamp tape cassette 
   codes, vinyl pressing numbers, sample origins). MongoDB allows schema evolution 
   instantly without running database migration scripts or altering table schemas.

4. Cloud Scalability:
   Our application connects directly to a 3-node MongoDB Atlas replica set 
   (cluster0.rc0j9kq.mongodb.net), giving automated failover, backups, and horizontal scaling."
